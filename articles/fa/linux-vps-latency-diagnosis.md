# عیب‌یابی تأخیر و Packet Loss در سرور مجازی لینوکس

بالا بودن Ping همیشه به معنای خرابی شبکه دیتاسنتر نیست. تأخیر ممکن است از شبکه کاربر، یکی از مسیرهای میانی، اپراتور ترانزیت، شبکه مقصد، ازدحام یا حتی خود برنامه ایجاد شود. برای تشخیص درست باید این لایه‌ها را از هم جدا کرد.

در این راهنما از ابزارهای استاندارد لینوکس استفاده می‌کنیم و تا جای ممکن از تغییرات مخرب شبکه پرهیز داریم.

## ۱. وضعیت اولیه سرور را ثبت کنید

ابتدا اطلاعات سیستم‌عامل، کارت شبکه و مسیرها را ذخیره کنید:

~~~bash
cat /etc/os-release
ip -br address
ip route
ip -s link
~~~

نام interface، آدرس IP، prefix، gateway و زمان اجرای تست را یادداشت کنید. نتیجه تست از داخل سرور به مقصد، لزوماً مسیر برگشت از سمت کاربر به سرور را توضیح نمی‌دهد؛ مسیر رفت و برگشت ممکن است متفاوت باشد.

## ۲. خطاهای رابط شبکه را بررسی کنید

~~~bash
ip -s link
ethtool -S ens3 2>/dev/null | head -n 80
~~~

به‌جای ens3 نام رابط واقعی سرور را قرار دهید. افزایش شمارنده‌های RX/TX errors، drops، overruns یا carrier ممکن است سرنخ مهمی باشد. بعضی درایورهای مجازی فقط بخشی از این شمارنده‌ها را ارائه می‌کنند؛ بنابراین ثابت بودن یک شمارنده به معنی سالم بودن تمام مسیر نیست.

## ۳. فقط به یک مقصد Ping نزنید

برای جلوگیری از اشتباه گرفتن محدودیت ICMP مقصد با اختلال عمومی شبکه، چند مقصد مستقل را آزمایش کنید:

~~~bash
ping -c 20 1.1.1.1
ping -c 20 8.8.8.8
ping -c 20 <destination-ip>
~~~

درصد packet loss و کمترین، میانگین و بیشترین RTT را ثبت کنید. برخی شبکه‌ها ترافیک ICMP را محدود یا کم‌اولویت می‌کنند؛ بنابراین نتیجه Ping را به‌تنهایی مبنای تشخیص قرار ندهید.

## ۴. مسیر را با MTR بررسی کنید

در Ubuntu و Debian:

~~~bash
sudo apt-get update
sudo apt-get install -y mtr-tiny
~~~

در خانواده AlmaLinux و RHEL، در صورت موجود بودن مخزن بسته:

~~~bash
sudo dnf install -y mtr
~~~

یک گزارش با تعداد نمونه مناسب بگیرید:

~~~bash
mtr -rwzc 100 <destination-ip>
~~~

در نسخه‌هایی که پشتیبانی می‌کنند، می‌توانید TCP را روی پورت واقعی برنامه آزمایش کنید:

~~~bash
mtr --tcp --port 443 -rwzc 100 <destination-ip>
~~~

### تفسیر درست خروجی MTR

اگر یک روتر میانی درصد Loss بالایی نشان دهد اما hopهای بعدی و مقصد نهایی بدون Loss باشند، احتمال محدودسازی پاسخ ICMP وجود دارد. این وضعیت به‌تنهایی ثابت نمی‌کند روتر بسته‌های عبوری را حذف می‌کند.

اما اگر Loss از یک نقطه به بعد در hopهای بعدی ادامه پیدا کند و در مقصد نهایی هم دیده شود، مسئله جدی‌تر است و باید با تست‌های دیگر تأیید شود. باز هم نباید صرفاً از روی یک خروجی، یک شرکت یا اپراتور مشخص را مقصر دانست.

## ۵. زمان اتصال TCP و HTTPS را جداگانه بسنجید

Ping زمان پاسخ ICMP را نشان می‌دهد، نه زمان برقراری اتصال واقعی HTTPS. برای اندازه‌گیری بخش‌های مختلف اتصال:

~~~bash
curl -sS -o /dev/null -w 'dns=%{time_namelookup}s connect=%{time_connect}s tls=%{time_appconnect}s ttfb=%{time_starttransfer}s total=%{time_total}s\n' https://example.com/
~~~

این خروجی زمان DNS، اتصال TCP، مذاکره TLS، دریافت اولین بایت و کل فرایند را جدا می‌کند.

برای نتیجه قابل اتکا، تست را چند بار اجرا کنید و میانگین و پراکندگی نتایج را ثبت کنید. یک نمونه منفرد ممکن است تحت تأثیر کش DNS، بار لحظه‌ای یا وضعیت شبکه مقصد باشد.

## ۶. Retransmissionهای TCP را بررسی کنید

~~~bash
nstat -az | grep -Ei 'Retrans|Timeout|ListenDrops'
ss -s
ss -ti
~~~

این دستورات آمار TCP و وضعیت socketها را نمایش می‌دهند. بهتر است دو snapshot با فاصله زمانی مشخص تهیه کنید؛ چون بسیاری از شمارنده‌ها از زمان boot تجمعی هستند و عدد مطلق به‌تنهایی چندان گویا نیست.

## ۷. تست را در هر دو جهت انجام دهید

برای یک بررسی قابل دفاع، دست‌کم این تست‌ها را اجرا کنید:

1. از VPS به سمت IP یا سرویس مقصد.
2. از شبکه کاربر به سمت IP عمومی VPS.
3. از VPS به چند مقصد مستقل دیگر.

اگر ICMP در یکی از شبکه‌ها فیلتر شده است، TCP probe روی پورت واقعی برنامه تصویر کاربردی‌تری می‌دهد. همچنین یکسان فرض کردن مسیر رفت و برگشت می‌تواند نتیجه‌گیری را اشتباه کند.

## ۸. گزارش فنی قابل بازتولید بسازید

برای گزارش اختلال این اطلاعات را ضمیمه کنید:

- تاریخ، ساعت و منطقه زمانی اجرای تست
- موقعیت تقریبی مبدأ و مقصد
- IP مقصد و پروتکل/پورت آزمایش‌شده
- خروجی MTR با تعداد چرخه کافی
- خلاصه Ping و تعداد بسته‌های ارسال‌شده
- خروجی شمارنده‌های رابط شبکه
- زمان‌های DNS، TCP، TLS و TTFB در صورت ارتباط با وب
- اینکه تست از داخل VPS انجام شده یا از شبکه کاربر

پیش از انتشار عمومی، IPهای عمومی و اطلاعات حساس را در صورت نیاز حذف یا مخفی کنید.

## جمع‌بندی عملی
